# Omnipotens documentation

人が読む成果物は、原則として **PDFとHTMLの両方** を生成する。PDFをSlackなどへの直接添付の基本とし、HTMLは手元のブラウザでも読める単体ファイルにする。Webの置き場やホスティングを前提にしない。ユーザーが片方の形式だけを指定した場合は、その指定を優先する。

## 入力と範囲

- 指定された資料と判断を整理する。資料化だけの依頼から、新たな採点、全分析の再実行、未選択の工程を追加しない。
- Omnipotensの最終レポートでは、同じ実行の `omnipotens-summary.json`、ソースマニフェスト、選択済み工程の成果物を使う。既存の判断モード、対象読者、証拠範囲、未解決事項を引き継ぐ。
- 既存の `new` / `operations` の区別を保つ。資料化のために運用専用の評価観点を新規へ追加しない。
- 原文やJSONを根拠の正本として残し、組版の都合で点数、確度、`improve` / `hold`、不足情報、不足実装を書き換えない。未知をゼロや平均値で埋めない。
- 入力の分類、出力先、共有先が既に確定していれば引き継ぐ。新しい外部送信先、ホスティング、会社の許可されていないアプリを資料生成の前提にしない。

## 生成するもの

最終レポートの標準出力は次のとおり。単独の設計・比較資料では同じ出力フォルダで内容を表す共通のファイル名を使う。

| ファイル | 用途 |
| --- | --- |
| `report/omnipotens-final.html` | 既存の決定的packagerが出力する詳細レポート。構造とJSON契約を保持する |
| `report/omnipotens-sharing.html` | 本スキルが生成する、必要な内容を単体で読めるスマホ向け配布版 |
| `report/omnipotens-final.pdf` | 配布版HTMLと同じ内容を収めたスマホ向けPDF |
| `report/omnipotens-documentation.manifest.json` | 入力・出力のハッシュ、生成方法、確認・配送状態 |

短く見る価値がある場合は、結論をまとめた `report/omnipotens-preview.png` も作る。画像は全文や根拠の代用にしない。MarkdownやTXTは編集・追跡用に保持できるが、依頼されたPDF/HTMLの代わりに納品完了としない。

## 資料を組み立てる

1. 読者が判断したいことと結論を先頭に置く。対象、版・日付、判断モード、分析状態、証拠の限界を短く添える。
2. [assets/document.html](assets/document.html) を組版の出発点として使い、資料に必要なカード・図・節だけを残す。テンプレートの説明を分析結果として流用しない。
3. 本文は日本語を基本とし、1列、本文16～18 CSS px程度、十分な行間を目安にする。横に広い表をそのまま縮小せず、項目ごとの見出し付きカードや小さな比較表に組み替える。
4. 結論、判断理由、根拠、次の判断、不足情報、不足実装を追えるようにする。色だけで状態や評価を伝えない。
5. Vitia 2.0.0の評価を含む場合、価値とパフォーマンスを独立して表示する。平均・積・総合点へ合成しない。対象者、根拠、確度、未評価を並記する。旧形式の入力を見た目だけで2.0.0へ変換しない。
6. HTMLの折りたたみや切替に依存する内容は、PDFでは静的に読める形に展開する。長い資料は節ごとに改ページし、重要な但し書きや根拠を切り落としてページ数を合わせない。

最終レポートには [Omnipotensの表示契約](../omnipotens/references/report-format.md) を適用する。`学生・初学者向け` と `高解像度データ` の総合評価・全項目サマリを保持し、その後に `各レイヤでの解析データは以下` を置く。PDFでは両プロフィールを見出し付きで順に収める。明示的に指定された読者向けの抜粋版なら、抜粋範囲と省略した内容を表紙に表示する。

## HTMLからPDFを作る

[references/rendering.md](references/rendering.md) に沿って、利用可能で許可されたローカルのレンダラーで生成する。CSSの印刷設定、日本語フォント、図の静的化、全ページの見た目の確認までを成果物作成に含める。

HTMLの完成だけでPDF生成済みと扱わない。PDFレンダラーが使えなければ、完成したHTMLは保持し、PDFを `blocked` として不足している手段を報告する。Web公開やオンライン変換サービスへ黙って切り替えない。

## 最終確認と共有

- HTMLをスマホ幅で確認し、PDFの全ページを画像化して、文字欠け、はみ出し、極端な空白、日本語の豆腐、図表の読みにくさを直す。抽出テキストだけでは見た目の確認済みとしない。
- PDFとHTMLで、採点・判断・根拠・対象範囲・不足事項が一致することを確認する。生成時刻と入力・最終成果物のSHA-256、レンダラーと版、使った設定、確認範囲をマニフェストへ記録する。
- Slackなどで共有する依頼がある場合、許可済みの会話へPDFを直接添付し、必要に応じてHTMLと要約画像も添える。投稿本文には結論と判断してほしい点を短く載せる。ローカルパスやリンクだけで配送済みとしない。
- 外部送信は現在の共有権限と実際の入力ゲートに従う。送信が許可されていない場合は、生成済みファイルを返して共有処理を分ける。生成の依頼だけから投稿を行わない。
- API受付、配送記録、実機の添付プレビューは別々に扱う。確認していない状態を成功にしない。差し替え時は最終版のハッシュと配送記録を対応させる。
