# ローカルでのHTML / PDF生成

## 出力の責務

既存の `omnipotens-report.mjs` は詳細HTML、段階別HTML、解析サマリJSON、入力マニフェストを出す。PDFや配布版HTMLを自動生成するコマンドではない。選択済みの `core.report` をまとめるときは既存コマンドを実行した後、本スキルで配布版HTMLとPDFを生成する。資料化のみの依頼では、既存成果物を使い、分析パイプラインを再実行しない。

配布版は、結論の確認に必要な図・本文・根拠の説明をファイル内に収める。詳細HTMLや元データへの参照を付けてもよいが、添付されていない別ファイルを開かなければ重要な判断が読めない構成にしない。引用元へのリンクと、別ファイルへの依存を区別する。

## HTMLを自己完結させる

- UTF-8、`lang="ja"`、viewport、意味のある見出し順を指定する。タイトルは資料と版が分かるものにする。
- CSSを埋め込む。必要な画像・図は検査済みのデータURIまたは静的SVGとして埋め込む。CDN、外部フォント、外部スクリプト、アクセス解析、ネットワーク取得を必要にしない。
- 入力の文字列をHTMLへ埋め込む際はエスケープする。元資料のHTML・SVG・スクリプトを実行可能な状態で直接挿入しない。
- 日本語を描画できるローカルフォントを使う。再配布できるフォントを持つ場合だけ埋め込み、ライセンスと出典を記録する。
- 320～430 CSS px程度の幅を目安に確認する。長いURL・識別子は折り返す。表の比較関係を保ちつつ、横長の列はラベル付きカードに分ける。
- 図は少なくとも判断に必要な部分を静的に描画する。Mermaidのソースコードや対話グラフへのリンクだけを、読める図として納品しない。
- 切替を使う場合も、JavaScriptなしで主要内容を読めるようにする。印刷時に両読者プロフィール、検索で隠れた節、折りたたみ内の根拠を含める。CSSだけで閉じた `details` の内容を表示できると仮定せず、印刷前の静的版では `open` にするか通常の節へ展開する。

## PDFへの変換

既存環境で利用できる、会社で許可されたローカルのHTML-to-PDFレンダラーを使う。ブラウザ操作・ツール利用が禁止されている環境では、その制約を解除せず利用可能な別のローカル手段を選ぶ。利用可能な手段がなければPDF生成だけをブロックとして報告する。

基本手順:

1. 配布版HTMLを完成させ、画像・フォントの準備完了後に変換する。
2. HTMLの `@page` を尊重する。初期値は **幅100 mm × 高さ178 mm、余白6 mm** 程度。短いページを積み重ね、本文12 pt程度を目安に調整する。A4への固定や「用紙に収める」自動縮小を既定にしない。
3. ブラウザのURL・印刷日時のヘッダー／フッターを無効にする。必要な資料名、版、ページ番号は資料側で設計する。
4. 色の有無に依存せず読める図表にする。カードが1ページを超える場合は分割を許可し、短い評価カードだけで不用意な改ページを避ける。
5. 文字を検索・選択できるPDFを生成する。長いスクリーンショットをPDFに貼るだけの実装は選ばない。
6. 生成先を一時ファイルにし、PDFの作成成功と確認後に最終名へ移す。既存成果物が他作業のものなら上書きしない。

例えば、承認済みChromium系ブラウザをCLIで使える場合は、シェルを介さない引数配列で次の引数を渡す。実行ファイルは実在を確認して指定し、固定インストール先を仮定しない。

```text
--headless
--no-pdf-header-footer
--print-to-pdf=<absolute-temporary-output.pdf>
--user-data-dir=<dedicated-temporary-profile>
<file-URL-of-sharing.html>
```

通常使っているブラウザのプロフィールを流用しない。タイムアウトと終了コードを確認し、自分が起動したプロセスと一時プロフィールだけを終了・片付ける。Windowsではバックグラウンドプロセスを非表示で起動する。レンダラーの隔離機能を無効にしない。変換中に外部URLを開く構成を避ける。

CLIオプションや印刷仕様はインストール済みバージョンで確認する。実際の起動引数・設定と版をマニフェストへ記録する。ユーザーが再現できる程度の記録でよく、社内絶対パスや秘密を配布本文へ埋め込まない。

## 確認する内容

- HTML: スマホ幅、拡大時の折返し、キー操作、図・画像・内部リンク、オフラインで必要な本文が読めること。
- PDF: 全ページの描画画像を確認し、文字欠け、日本語フォント、余白、改ページ、図表の縮小、空白ページを直す。利用可能ならPopplerの `pdftoppm` などで画像化する。
- 内容: 総合評価、両サマリプロフィール、選択された分析、根拠、未知、確度、改善／維持の判断が同じ入力を参照していること。
- Vitia: 価値とパフォーマンスの軸を混ぜていないこと。PDF化によって未評価や留保が消えていないこと。
- メタデータ: 表紙の版、入力の版、最終成果物のハッシュが一致すること。古いPDFを新しいHTMLと組み合わせないこと。

実機Slackでの添付プレビューを見ていなければ、その状態は未確認と記録する。ローカルでのPDF描画確認と混同しない。

## 生成記録

`omnipotens-documentation.manifest.json` には、少なくとも次を記録する。既存packagerの `omnipotens-final.manifest.json` を書き換えたり、PDFも生成した証拠として流用したりしない。

- 資料名、版、生成時刻（タイムゾーン付き）、分類、判断モード、全文／抜粋の範囲。
- 今回使った入力のプロジェクト相対パスとSHA-256。最終解析では正本サマリJSONと既存packagerのマニフェストを含める。
- 生成したHTML・PDF・任意の画像の相対パスとSHA-256。各形式の生成状態と失敗理由。
- 実際のレンダラーと版、用紙・余白・読者プロフィール、生成方法。
- 確認したHTML幅、PDFページ数と画像確認範囲、未確認の項目。
- 共有を実施した場合だけ、送信した最終ファイルのハッシュと配送結果。秘密や期限付きURLを記録しない。

生成記録自体のハッシュをその記録へ含める必要はない。内部の追跡用記録を、そのまま社外向け資料へ添付しない。
